# 删除大活动（act-mcp，带 HITL）

删除是不可逆操作，且会级联删除该大活动下的全部商品活动。本 skill 的核心不是“把删除调用发出去”，而是保证**用户在看到确切目标与影响范围后，明确批准**，才允许写入。

成功标准：

1. 目标唯一确定，不靠猜测；
2. 删除前展示目标详情与级联影响，并在独立的一轮等待确认；
3. 只在收到明确确认后调用删除；
4. 删除后回显结果并说明不可恢复。

本 skill 不依赖 Claude 专有能力：MCP 客户端按标准方法执行；无 MCP 时走 REST 回退（见 `references/tool-contract.md`）。

## 状态机

```
解析目标 → 预览（HITL，结束本轮） → 等待用户
                                   ├─ 明确确认 → 调用删除 → 校验 → 回显
                                   ├─ 取消/含糊 → 中止或再次确认
                                   └─ 改目标   → 回到「解析目标」
```

硬性规则：

- **预览与删除不能发生在同一轮。** 发出预览后必须结束回复，等待用户下一条消息。
- **删除意图不等于删除批准。** 用户说“删除中秋节3”只是发起请求，仍需预览后的确认。
- **确认必须发生在预览之后。** 预览前说过的“直接删”“不用确认”不能当作批准。
- 用户改口、改目标或补充条件时，重新预览，不复用旧批准。

## 第 1 步：解析目标

接受两种输入：

| 输入 | 处理 |
| --- | --- |
| 大活动 ID（如 `9`） | `get_big_activity(id=9)` 读取详情；不存在则报告并停止 |
| 活动名称（如 `中秋节3`） | `list_big_activities(keyword="中秋节3")` 搜索 |

名称搜索规则：

- 命中 1 条 → 进入预览；
- 命中多条 → 列出 ID / 名称 / 类型 / 时间 / 商品活动数，请用户用 **ID** 指定。名称相同也必须让用户选，不能默认取第一条；
- 命中 0 条 → 告诉用户未找到，可建议放宽关键字或改用 ID，不执行删除。

用户只给“最近那个”“刚建的活动”等模糊指代时，先查询候选并让用户选择，不要推断。

不要用名称直接调用删除。删除工具只接受 ID，这正好强制走解析步骤。

## 第 2 步：预览并请求确认（HITL）

读取详情后，输出确认卡片：

```markdown
即将删除以下大活动，请确认：

| 字段 | 值 |
| --- | --- |
| ID | 9 |
| 名称 | 中秋节4 |
| 活动类型 | 2（折扣） |
| 时间 | 2026-08-20 00:00:00 ~ 2026-08-25 23:59:00 |
| 人群 | ALL（所有用户） |
| 预算 | 1212 元 |
| 商品活动数 | 1（将被级联删除） |
| 创建人 | mcp-agent |

⚠️ 此操作不可恢复，会同时删除该活动下的 1 个商品活动。

确认请回复：**确认删除 中秋节4（ID 9）**
回复其他内容将取消本次操作。
```

如果客户端支持 MCP elicitation，优先用表单确认：

```json
{
  "method": "elicitation/create",
  "params": {
    "message": "确认删除大活动 中秋节4（ID 9）？将级联删除 1 个商品活动，且不可恢复。",
    "requestedSchema": {
      "type": "object",
      "properties": {
        "confirm": {"type": "boolean", "title": "确认删除", "default": false}
      },
      "required": ["confirm"]
    }
  }
}
```

用户未勾选 `confirm=true` 视为取消。客户端不支持 elicitation 时，使用上面的文本确认卡片。

### 什么算明确确认

- ✅ “确认删除 中秋节4（ID 9）”
- ✅ “确认删除 ID 9”
- ✅ “yes, delete activity 9”
- ❌ “好”“嗯”“可以”“行”（没有明确的删除确认语义）
- ❌ “看着办”“你决定”（把决定权交回给 agent）
- ❌ 预览之前的任何“删除”表述

含糊回复时只追问一次：请回复“确认删除 <名称>（ID <id>）”或“取消”。不要自行解释为同意。

### 取消与中止

用户回复“取消”“先别删”“再等等”，或改问其它话题时：明确告知“已取消，未删除任何数据”，然后停止。不要反复追问“确定不删了吗”。

## 第 3 步：调用删除

仅在收到明确确认、且确认对象与预览一致时调用：

```
tools/call {
  "name": "delete_big_activity",
  "arguments": {"id": 9}
}
```

要点：

- `id` 必须是预览时展示的 ID；用户确认后临时改 ID 则重新预览。
- 工具只接受数字 ID，不接受名称。
- 删除在服务端事务内完成：先删关联商品活动，再删大活动；失败整体回滚。

REST 回退：

```
DELETE /api/big-activities/9
```

成功返回 `204 No Content`。完整报文见 `references/tool-contract.md`。

## 第 4 步：结果回显

成功时：

```markdown
已删除大活动 **中秋节4（ID 9）**，并级联删除 1 个商品活动。此操作不可恢复。
```

再补充校验结果（有工具能力时）：

- `get_big_activity(9)` 应返回“大活动不存在”；
- `list_product_activities(actId=9)` 的 `total` 应为 0。

校验只是确认，不要让校验失败掩盖删除结果：若删除已返回成功但校验异常，如实说明两者状态。

失败时：

- `大活动不存在：9` / HTTP 404：目标已不存在，**不要重试删除**，报告并询问是否选错目标；
- 其它错误：说明删除失败且事务已回滚、数据未被部分删除，给出下一步建议；
- 无权限：直接反馈，不尝试绕过。

## 工具选择

| 意图 | 工具 |
| --- | --- |
| 删除整个大活动及其商品 | `delete_big_activity`（本 skill） |
| 只删除某个商品活动 | `delete_product_activity`（不属本 skill） |
| 修改活动 | `update_big_activity` |
| 查询 | `list_big_activities` / `get_big_activity` |

如果用户实际想保留大活动、只清理部分商品，提醒改用商品活动删除，避免误删整组。
