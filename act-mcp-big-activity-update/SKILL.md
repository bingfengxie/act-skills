# 编辑大活动（act-mcp，带 HITL）

编辑会改写线上配置。本 skill 保证用户在看到**具体字段的当前值与修改后值**、并且明确批准之后，才提交更新。

成功标准：

1. 目标唯一确定，不在名称歧义时猜测；
2. 只提交用户要求修改的字段，未要求的字段保持原值；
3. 按“合并后的最终状态”做跨字段校验（尤其是开始/结束时间）；
4. 修改前预览差异并在独立一轮等待确认；
5. 修改后回显差异并校验结果。

本 skill 不依赖 Claude 专有能力：MCP 客户端按标准方法执行；无 MCP 时走 REST 回退（见 `references/tool-contract.md`）。

## 状态机

```
解析目标 → 读取当前值 → 计算差异 → 预览（HITL，结束本轮） → 等待用户
                                                        ├─ 明确确认 → 更新 → 校验 → 回显
                                                        ├─ 取消/含糊 → 中止或再问一次
                                                        └─ 改内容/改目标 → 重新计算并预览
```

硬性规则：

- **预览与更新不能发生在同一轮。** 发出差异卡片后必须结束回复。
- **修改意图不等于修改批准。** 用户说“把结束时间改到 9 月 1 日”只是发起请求。
- **批准必须发生在预览之后，且指向预览过的目标。**
- 用户补充或修改要求时，重新计算差异并重新预览，不复用旧批准。
- 只提交差异字段；不要把当前值整包回写。

## 第 1 步：解析目标

| 输入 | 处理 |
| --- | --- |
| 大活动 ID | `get_big_activity(id)`；不存在则报告并停止 |
| 活动名称 | `list_big_activities(keyword=...)` 搜索 |

名称命中 1 条 → 继续；命中多条 → 列出 ID / 名称 / 类型 / 时间 / 商品活动数，请用户用 ID 指定；命中 0 条 → 报告未找到，不执行更新。

## 第 2 步：收集修改项并映射

支持的字段：

| 字段 | 规则 |
| --- | --- |
| `name` | 1–100 字符 |
| `actType` | 1–5，中文映射见下 |
| `startTime` | 规范化为 `yyyy-MM-ddTHH:mm` |
| `endTime` | 同上，且最终状态下必须晚于 `startTime` |
| `audienceScope` | `ALL` / `NEW` |
| `budget` | ≥ 0，最多 12 位整数 + 2 位小数 |
| `collectionDiscountJson` | 合法 JSON；传空值会归一化为 `{}` |
| `operator` | ≤ 50 字符，缺省 `mcp-agent` |

中文值映射：

```
满减/满减活动 → 1    折扣/折扣活动 → 2    秒杀/秒杀活动 → 3
优惠券/优惠券活动 → 4    组合/组合优惠/叠加 → 5
全部/所有用户/全量 → ALL    新客/仅新客/新人 → NEW
```

用户没有说明要改哪个字段时，先问“要修改哪些字段”，不要遍历所有字段让用户重填。

### 修改活动类型的影响

`actType` 修改**不会**同步修改已有商品活动的类型；商品活动保留各自库中的 `act_type`。若用户预期级联，先说明这一行为，必要时另行更新商品活动。

## 第 3 步：计算差异并校验

优先运行脚本（Python 3 标准库，`-I` 隔离执行）：

```bash
python3 -I scripts/preview_update.py current.json changes.json
```

- `current.json`：`get_big_activity` 的返回值。
- `changes.json`：用户要求修改的字段，可继续使用中文值，例如
  `{"endTime": "2026-9-1 23:59", "budget": 2000}`。

脚本输出 `ok`、`errors`、`warnings`、`diff`、`tool_arguments`：

- `ok = false`：把 `errors` 告诉用户；不要调用工具。
- `ok = true`：用 `diff` 生成预览卡片，用 `tool_arguments` 调用。
- `no_changes = true`：说明没有实际变化，不调用工具。

脚本不可用时按下列规则人工核对：

1. 未提供的字段沿用当前值；
2. 用**合并后的最终状态**校验开始/结束时间；
3. 只把发生变化的字段放进提交参数；
4. 数值、时间、JSON 做语义比较（`1212` 与 `1212.00` 不算变化）。

## 第 4 步：预览差异（HITL）

```markdown
即将修改大活动 **中秋节4（ID 9）**：

| 字段 | 当前值 | 修改后 |
| --- | --- | --- |
| 结束时间 | 2026-08-25 23:59:00 | 2026-09-01 23:59:00 |
| 预算 | 1212 元 | 2000 元 |

其余字段保持不变。修改后开始时间 2026-08-20 00:00:00 早于结束时间，校验通过。

确认请回复：**确认修改 中秋节4（ID 9）**
回复其他内容将取消本次操作。
```

要求：

- 只列实际变化的字段；未变化字段用一句“其余字段保持不变”概括；
- 时间展示到秒，与库中一致；用户若以秒级改动，说明按分钟精度提交；
- 涉及 `actType` 时附上“商品活动类型不会级联修改”的提示；
- 跨字段校验结果显式写出（通过或冲突）。

客户端支持 MCP elicitation 时，用布尔表单确认（模板见 `references/tool-contract.md`）；不支持时用文本卡片。

### 什么算明确确认

- ✅ “确认修改 中秋节4（ID 9）”
- ✅ “确认修改 ID 9”
- ✅ “yes, update activity 9”
- ❌ “好”“嗯”“可以”“行”
- ❌ “看着办”“你决定”
- ❌ 预览之前的任何“改吧/直接改”表述

含糊回复只追问一次：请回复“确认修改 <名称>（ID <id>）”或“取消”。

### 取消与改口

- “取消”“先不改了” → 明确告知未提交任何修改，停止。
- 用户提出新的修改内容 → 重新计算差异，重新预览，不复用旧批准。
- 用户改目标 ID → 回到第 1 步重新读取当前值。

## 第 5 步：提交更新

仅在收到明确确认、且目标与预览一致时调用：

```
tools/call {
  "name": "update_big_activity",
  "arguments": {
    "id": 9,
    "endTime": "2026-09-01T23:59",
    "budget": 2000,
    "operator": "mcp-agent"
  }
}
```

要点：

- 只传差异字段；MCP 工具会用库中现存值补齐其余字段。
- `id` 必须是预览过的 ID。
- 时间为 `yyyy-MM-ddTHH:mm`；金额为数字；JSON 字段为字符串。

REST 回退（注意差异）：`PUT /api/big-activities` **要求完整请求体**（`id` + 全部必填字段），不支持部分更新。用当前值补齐未修改字段后再提交。完整示例见 `references/tool-contract.md`。

## 第 6 步：回显并校验

```markdown
已更新大活动 **中秋节4（ID 9）**：

| 字段 | 修改前 | 修改后 |
| --- | --- | --- |
| 结束时间 | 2026-08-25 23:59:00 | 2026-09-01 23:59:00 |
| 预算 | 1212 元 | 2000 元 |

操作人：mcp-agent。本次未修改商品活动。
```

再用 `get_big_activity(id)` 复核：

- 变更字段与预览一致；
- 未变更字段保持原值；
- `updatedBy` / `updatedAt` 已刷新。

复核不一致时如实报告，不要用“应该已经生效”带过。

## 失败处理

| 返回 | 处理 |
| --- | --- |
| `大活动不存在：<id>` / 404 | 目标已不存在，不重试；询问是否选错目标 |
| `结束时间必须晚于开始时间` | 指出与当前另一侧时间的冲突，请用户调整 |
| 字段校验错误 | 翻译成具体字段与格式要求，修正后重新预览 |
| 无权限 | 如实反馈，不绕过 |
| 其它错误 | 说明未发生部分更新（单事务），建议重试 |
